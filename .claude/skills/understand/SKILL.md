# 理解确认技能

## 核心目标

这个技能的目标不是直接解决问题，而是先确认 AI 是否真的理解了用户当前这一轮的真实意图。

当用户很在意“不要误解我”“不要跑偏”“先理解再做”时，优先使用这个技能。

## 适用场景

**仅在以下情况显式触发**（用户必须明确要求）：

- 用户主动说"先理解一下"、"确认你的理解"、"我担心你会误解"
- 用户要求先"想清楚再动手"
- 用户刚纠正了 AI 的理解，AI 需要重新对齐

**以下情况不触发**（即使是非简单请求）：

- 非简单请求但意图明确时
- 用户只是描述需求而未要求确认理解时
- AI 即将写计划或开始实现时

## 强制规则

触发这个技能后，必须先做“理解确认”，不能直接继续规划、实现或长篇解释。

如果用户修正了理解，必须重新复述更新后的理解，并再次等待确认。

只有在用户明确认可当前理解后，才能继续后续工作。

## 固定输出格式

默认使用中文，并严格按下面结构输出：

```markdown
我先确认一下我的理解：

1. 你的核心目标是：...
2. 当前范围是：...
3. 明确约束 / 不希望我做的是：...
4. 我认为最容易误解的点是：...
5. 如果我的理解对，下一步我会：...

请你确认我的理解是否准确；如果不对，你直接纠正我。
```

## 使用原则

### 1. 先抓“意图”，不是先抓“实现”

优先确认这些内容：

- 用户最终想达到什么结果
- 用户为什么现在关心这个问题
- 当前阶段到底是理解、方案还是执行
- 用户明确不希望我做什么
- 用户希望我复用现有逻辑，还是允许重新设计

### 2. 必须指出“最容易误解的点”

不能只做一句复述，必须主动指出高风险误解点。

常见误解包括：

- 把理解需求误当成实现需求
- 把外层问题误解成底层问题
- 过度设计简单需求
- 用户只想读源码，却被带到重构方案
- 用户要求复用现有逻辑，却被带到新抽象
- 用户要求不改源码，却被带到实现改动

### 3. 用户一旦改口，要显式更新理解

当用户推进过程中调整重点时，要明确说出变化：

- 我更新一下理解，和刚才相比，现在重点变成 ...
- 我之前把重点放在 ...，但你现在真正要的是 ...

### 4. 不要假装自己已经完全懂了

如果还有不确定的地方，要明确指出。

不要在“用户非常在意理解是否准确”的场景下，默默选择一种解释直接继续。

## 示例

### 示例 1：需求从实现转为理解

**用户：**

因为 TUI 不好 debug，我想跳过它来理解真实的外层逻辑。

**期望输出：**

```markdown
我先确认一下我的理解：

1. 你的核心目标是：为了更稳定地 debug Claude Code 的真实执行链路，想绕过 TUI 的渲染层。
2. 当前范围是：先理解和模拟 TUI 之外的非渲染编排逻辑，而不是直接重写一个新客户端。
3. 明确约束 / 不希望我做的是：不要自己发明一套新的业务逻辑，不要偏离现有源码的真实行为。
4. 我认为最容易误解的点是：我可能会把重点放到 queryLoop 内核，或者误以为你要完整复刻 REPL。
5. 如果我的理解对，下一步我会：继续拆清楚 REPL 里哪些属于渲染，哪些属于必须保留的编排逻辑。

请你确认我的理解是否准确；如果不对，你直接纠正我。
```

### 示例 2：用户增加新约束

**用户：**

不要改 src，也不要自己写一套 session 管理。

**期望输出：**

```markdown
我更新一下理解：

1. 你的核心目标不变，还是为了跳过 TUI 来 debug 真实外层逻辑。
2. 当前范围进一步收缩为：只允许在 debug 目录下做脚本级模拟。
3. 明确约束 / 不希望我做的是：不能改 src，不能自己重新设计 session 或 harness。
4. 我认为最容易误解的点是：如果我继续抽象公共层，或者自己维护新的状态流，就已经偏离你的目标了。
5. 如果我的理解对，下一步我会：只围绕现有 REPL 非渲染逻辑来整理方案。

请你确认我的理解是否准确；如果不对，你直接纠正我。
```

## 成功标准

这个技能生效时，用户应该能很快只做两种回应之一：

- 对，就是这个意思。
- 不对，我真正要的是 ...

这样可以在 AI 跑偏之前，先把方向对齐。
